# 连续写作格式兼容修复验证

日期：2026-10-16。针对“接着写4章，每章大约3000字”在保存、检查1章后报“连续写作回复字段不正确”的问题。

## 现场与根因

只读核对本机记录：原任务目标为第2—5章，第2章已保存并检查，停在生成第3章，已报告61,220 Token、5次请求，总预算200,000。历史写作路径没有保存失败返回，无法追溯两次历史回复各自的完整结构。

在一致性备份的隔离副本上限一次真实请求复现：返回包含标题、3065字符正文、scenes、states、majorChange=false、reason，以及额外的顶层 `type: "json_object"`。旧解析器因这个标记拒绝整章。该次调用报告14,139 Token。原生产任务、正文和配置未修改。

修复后将同一份回复在隔离副本离线重放，标题与正文逐字保存成功。重放在进入检查时由测试桩停止，没有继续调用真实接口，不能把这项重放算作完整四章验证。私有诊断数据库、原始正文与临时脚本已删除，只保留无正文、无凭据的结构证据：[重放证据](writing-format-replay-20261016.json)。

## 修复范围

- 只兼容完整扁平规划/章节结果中精确的 `type: "json_object"` 冗余标记；其余字段仍校验，不吞掉嵌套外壳中的决策，不接受未知类型或额外字段。
- 重大创作变更仍暂停等待作者，既有正文与并发修改保护不变；兼容处理不增加模型调用，不重新生成已返回的正文。
- 格式失败保留最近一次原始返回、阶段和章节位置用于诊断，不作为可应用章节或自动重放来源。超过300,000字符明确记录截断；常规工作区轮询不传送原始正文。失败路径与成功路径均脱敏当前调用使用的密钥。
- 保留既有任务的保存进度与预算；更新后可在原任务继续，不需要重建任务。
